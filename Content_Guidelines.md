## Voice

Sean's voice is direct, confident, and grounded. He writes like someone who builds things, not someone who comments on people who build things. The tone sits between a sharp technical blog and a founder's journal.

### Voice Attributes

| Attribute | Description |
|-----------|-------------|
| Direct | Get to the point. No filler paragraphs, no throat-clearing introductions. |
| Technical | Comfortable with code, architecture, and systems-level detail. Never dumbs things down but always explains context. |
| Opinionated | Takes clear positions. Does not hedge with "it depends" when he has a real answer. |
| Authentic | Speaks from firsthand experience. References real projects, real failures, real decisions. |
| Concise | Short sentences. Short paragraphs. Every word earns its place. |

### Voice Is Not

- Academic or formal
- Corporate or marketing-speak
- Humble-braggy or performative
- Preachy or lecturing
- Vague or wishy-washy

## Tone by Content Type

### Guides

Practical and instructional. The reader has a problem and needs a solution. Lead with the outcome, then show the steps. Include real code. Skip the backstory unless it directly helps the reader.

### Blog Posts

Conversational and reflective. Sean is thinking out loud. He can share what went wrong, what surprised him, what he would do differently. First person is expected. Personality shows through.

### Articles

More structured than blog posts. Still opinionated but backed by reasoning. These are the pieces that could be shared in a Slack channel and spark a conversation.

### Event Recaps

Informal and observational. What happened, what stood out, who he met, what he took away. Photos and links are encouraged. Keep it brief unless the event genuinely warrants depth.

## Writing Standards

### Structure

- Lead with the point. The first sentence of any piece should tell the reader why they should keep reading.
- Use headings to break up sections. A reader skimming should get the gist from headings alone.
- Use code blocks for anything technical. Inline code for references, fenced blocks for examples.
- Use lists when presenting more than two related items.
- Keep paragraphs to 3-4 sentences maximum.

### Language

- Write in American English.
- Use contractions naturally (don't, can't, won't, it's).
- Avoid jargon without context. If a term is niche, explain it on first use.
- Never use "utilize" when "use" works. Never use "leverage" as a verb. Never use "synergy."
- No exclamation marks in body text. They weaken the writing.
- Use "Sean" in third-person contexts (about page, bios). Use "I" in all authored content.

### Technical Content

- All code examples must be working, tested, and current.
- Specify the language in every fenced code block.
- Show the file path above or inside the code block when the location matters.
- Prefer complete examples over snippets that cannot run in isolation.
- Pin dependency versions when they matter to the reader.
- If a guide targets a specific version of a tool or framework, state that version in the opening paragraph.

### Titles & Headings

- Blog post titles are lowercase sentence case ("How I rebuilt our deploy pipeline").
- Guide titles start with a verb or describe the outcome ("Deploy to multiple clouds with Foltrac", "Set up W0rktree for your monorepo").
- Never use clickbait. No "You won't believe..." or "The one thing..." patterns.

### Dates & Time

- Use full month names (April 10, 2026) in published dates.
- Use relative time only when the content is recent and the relative reference will be updated.

### Images & Media

- Every image needs meaningful alt text.
- Screenshots should be cropped to show only what is relevant.
- Use WebP or AVIF format. Optimize before uploading.

## SEO & Metadata

- Every page needs a unique `title` and `description` in frontmatter.
- Descriptions are 120-160 characters, written as a complete sentence.
- Titles do not repeat the site name.
- Use a single `h1` per page. It should match or closely mirror the `title`.
- Internal links use relative paths. External links open in a new tab.

## Content Sean Does Not Publish

- Hot takes for engagement
- Sponsored content or undisclosed partnerships
- Content about other people's failures
- Anything he has not personally built, used, or experienced
